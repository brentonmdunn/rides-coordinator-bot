# Adding a new bot

The backend runs several Discord bots, each with its own application and token, in a single process and event loop. RideBot and StonesBot are the current examples. This guide walks through adding another one, using a placeholder bot called **NewBot** (`newbot`).

## How it fits together

- **Registry.** `backend/shared/core/bots.py` defines `BOT_REGISTRY`, with one `BotSpec` per bot. Each spec holds the token env var, the cog packages to load, the intents, and a kill-switch feature flag. Lifecycle, health, error reporting and the kill switch all read from it, so there's no other wiring to do.
- **Packages.** Each bot is a top-level package (`backend/ridebot/`, `backend/stonesbot/`) with its own `cogs/`, `services/`, `repositories/`, etc. Infrastructure every bot needs lives in `backend/shared/`.
- **Import boundaries.** `shared` never imports a bot package, and bot packages never import each other. `tests/unit/test_import_boundaries.py` enforces this for every package in the registry.
- **Bot context.** Each bot runs in its own asyncio task that sets `current_bot_var` (in `shared/core/bot_context.py`) first. Event handlers, slash commands and scheduled jobs inherit it, which is how shared code such as the error reporter and `@bot_enabled` knows which bot it's running under.

## Steps

### 1. Enum values

In `backend/shared/core/enums.py`:

```python
class BotName(StrEnum):
    RIDEBOT = "ridebot"
    STONESBOT = "stonesbot"
    NEWBOT = "newbot"


class FeatureFlagNames(StrEnum):
    RIDEBOT = "ridebot"
    STONESBOT = "stonesbot"
    NEWBOT = "newbot"  # kill switch
    ...
```

### 2. Kill-switch flag migration

Feature flags are seeded as **disabled** on startup, so a new flag would ship turned off. Add a data migration that decides the initial state. From `backend/`:

```bash
uv run alembic revision -m "add newbot feature flag"
```

Then write the SQL by hand; this isn't autogenerated. To start enabled:

```python
def upgrade() -> None:
    op.execute(
        sa.text(
            "INSERT INTO feature_flags (feature, enabled) "
            "SELECT 'newbot', 1 "
            "WHERE NOT EXISTS (SELECT 1 FROM feature_flags WHERE feature = 'newbot')"
        )
    )


def downgrade() -> None:
    op.execute(sa.text("DELETE FROM feature_flags WHERE feature = 'newbot'"))
```

`alembic/versions/8b2d3f0c5e21_add_stonesbot_flag.py` is a worked example that copies RideBot's current state instead.

### 3. Registry entry

In `backend/shared/core/bots.py`, add an intents factory that requests **only** what the bot's cogs need, then append a spec:

```python
def _newbot_intents() -> discord.Intents:
    intents = discord.Intents.default()
    intents.members = True  # privileged: must also be enabled in the developer portal
    return intents


BOT_REGISTRY: tuple[BotSpec, ...] = (
    ...,
    BotSpec(
        name=BotName.NEWBOT,
        token_env="NEWBOT_TOKEN",
        cog_packages=("newbot.cogs", "shared.cogs"),  # drop "shared.cogs" to skip /help
        intents=_newbot_intents,
        kill_switch_flag=FeatureFlagNames.NEWBOT,
    ),
)
```

Registry order is the fallback order for error reporting (see below). Optional fields:

- `priority_extensions`: module names loaded first within each package, e.g. `("job_scheduler",)`.
- `testing_cog_package`: a package loaded only when `APP_ENV=local`.

### 4. Package

```
backend/newbot/
  __init__.py          """NewBot: <purpose>."""
  cogs/__init__.py     every non-underscore module here is loaded as an extension
  services/            business logic (cogs stay thin)
  repositories/        DB access (@staticmethod, session as first arg)
```

- Models go in `backend/shared/core/models.py`. There's one database and one Alembic metadata.
- Gate slash commands with `@bot_enabled` from `shared.utils.checks`. It resolves the current bot's kill-switch flag at call time, so cogs never name their bot's flag.
- Event listeners (`@commands.Cog.listener()`) are **not** covered by `@bot_enabled`. Give them their own feature flag if they need one (StonesBot's reaction listener uses `EVENT_THREADS`).
- Follow the `CLAUDE.md` conventions: per-module loggers, `@log_cmd` on commands, `logger.exception` in `except` blocks.

### 5. Sharing code

If NewBot needs something that currently lives in another bot's package, **move it to `shared/`**. Never import it across packages; the boundary test will fail. Only promote code that is infrastructure or that at least two bots actually use.

### 6. Environment variables

- `backend/.env.example`: `NEWBOT_TOKEN=`
- `backend/Dockerfile.preprod`: `ENV NEWBOT_TOKEN=""`
- Server env files (`.env.preprod`, `.env.prod`) and your local `.env`

Token rules, applied at startup by `resolve_enabled_bots()`:

| Environment | Token unset or blank |
|---|---|
| `preprod` / `prod` | Logs `CRITICAL: NEWBOT_TOKEN is not set` and exits. The container never becomes healthy. |
| `local` | Logs a warning and skips NewBot; the other bots still start. |
| any, with `DISABLE_DISCORD_BOT=true` | Tokens aren't read; runs API-only. |

A set but invalid token exits in every environment.

### 7. Discord application

In the [Discord developer portal](https://discord.com/developers/applications):

1. Create an application for each environment (prod, preprod, and optionally a dev one), then add a bot user and copy its token.
2. Under **Bot → Privileged Gateway Intents**, enable whatever `_newbot_intents()` requests (Server Members, Message Content).
3. Under **OAuth2 → URL Generator**, select the scopes `bot` and `applications.commands`, plus the permissions the cogs need. Open the URL and add the bot to the server.
4. Give the bot **Send Messages** in the `ERROR_CHANNEL_ID` channel. Errors are posted by the bot where they happened.

### 8. Docs

- `docs/bot-commands.md`: the new bot's commands.
- `docs/feature-flags.md`: the `newbot` kill switch.
- `CLAUDE.md`: repository layout and registry description.

## Deploy order

1. Discord application setup (step 7).
2. Add `NEWBOT_TOKEN` to the server env files.
3. Deploy. The entrypoint runs migrations, which seeds the flag.

If you deploy before the token is set, startup exits and the deploy script rolls back.

## Verifying

- **`uv run pytest -q`.** `tests/unit/test_import_boundaries.py` now also checks `newbot/`. Add a registry test like the StonesBot ones in `tests/unit/test_bots_registry.py`.
- **`GET /health`.** It now reports NewBot:

  ```json
  {"status": "ok", "database": "connected", "bots": {"newbot": "connected", "ridebot": "connected", "stonesbot": "connected"}}
  ```

  Any enabled bot that isn't ready, or any cog that failed to load, returns **503**.
- **Logs.** Lines from NewBot's handlers carry `[bot:newbot]`, and startup logs `Synced N slash commands` per bot.
- **Errors.** Error reports from NewBot are prefixed `[newbot]`. If NewBot isn't ready, RideBot posts the report, then any other ready bot, then stderr.
